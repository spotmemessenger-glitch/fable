# Security review — encrypted notification payload (Priority 2)

Scope: the gated `EncryptedEnvelopeBuilder` + `envelope/notif-crypto.ts` seal
path. This is the review the owner must sign off **before**
`NOTIF_ENCRYPTED_PAYLOAD_ENABLED` may be turned on (ADR-008 §12). Until then the
content-less floor is the only live builder and this path is unreachable (it
throws before any crypto).

## What it does

Seals a rich, DEVICE-only notification payload so the push provider stays blind
while the device renders "Alice · 1 new message · [Reply][Mute]".

- **Construction:** X25519 **ECDH-ES(ephemeral, devicePub)** → **HKDF-SHA256**
  (salt=16B random, info=`spotme/notif-seal/v1`) → **AES-256-GCM** (iv=12B
  random, AAD=`spotme/notif-seal/v1|<notifId>`). Ephemeral-static sealed box —
  the same family as e2e_v2, **independently implemented**, Node `crypto` only,
  no hand-rolled primitives.
- **On the wire (`data.e`):** `{v, epk, salt, iv, ct‖tag}`, all base64url — opaque
  to FCM/APNs/Mozilla. A generic `title`/`body` remains as the visible fallback.

## Key custody — the property §12 turns on

| Key | Generated by | Lives where | Server sees |
|---|---|---|---|
| Device notification keypair | the DEVICE (WebCrypto `generateKey({name:'X25519'}, extractable=false)`) | on the device; private half NON-extractable | **public half only** (SPKI, registered) |
| Ephemeral seal keypair | the server, per seal | discarded when `sealRichPayload` returns | ephemeral public rides in `epk`; private never stored |

The server **never generates, reads, or persists a device private key.** The
isolation fence (`isolation.spec`) mechanically asserts: (a) key/seal primitives
appear ONLY in `notif-crypto.ts`; (b) no `notif(ication)PrivateKey` is persisted
anywhere; (c) the module imports nothing from the P1 signing/ratchet/x3dh/prekey/
e2e crypto; (d) with the flag off the builder throws before any crypto runs.

## The §12 question for the owner

ADR-008 §12 forbids **signing-key** generation/persistence/publication and the
X3DH/ratchet/prekey/multi-device programme until rollback-after-publication is
executable or separately authorised. This notification key is a **separate,
notification-scoped X25519 wrapping key**, not a messaging **signing** key, and
its **public** half is what gets registered. The decision to make is narrow:

> **Is registering a per-device PUBLIC X25519 notification wrapping key
> "key publication" in the §12 sense?**

Arguments it is **not**: it is a public encryption key (not a signing identity);
it authenticates nothing and binds no identity; it is domain-separated
(`spotme/notif-seal/v1`) from every messaging key; losing/rotating it degrades
gracefully to the content-less floor (no identity/history exposure); there is no
prekey/ratchet coupling. Residual concern to rule on: any public-key
registration is a small new **publication surface** and needs a rotation +
revocation story (below) before GA.

## Threats & mitigations

- **Provider reads the payload** → sealed; provider sees only opaque base64url.
- **Blob replayed against another notification** → AAD binds `notifId`; unseal
  fails (tested).
- **Foreign/tampered blob renders attacker text** → GCM auth failure throws;
  device falls back to the content-less floor (tested: wrong-key, tamper,
  bad-version all throw).
- **Server compromise leaks a device key** → impossible; the server holds no
  device private key, and ephemeral seal keys are discarded per call (forward
  secrecy across seals: each uses a fresh ephemeral + salt + iv).
- **Nonce reuse** → every seal draws a fresh 12B iv AND a fresh ephemeral key +
  16B salt, so the AES key itself differs per message (tested: no epk/iv/ct
  reuse across two seals of identical input).

## Preconditions before flipping `NOTIF_ENCRYPTED_PAYLOAD_ENABLED`

1. Owner sign-off on the §12 question above.
2. A device-key **registration** endpoint (public key only) with a **rotation +
   revocation** path, and pruning on device de-registration.
3. Device-side unseal in the Android `FirebaseMessagingService` / iOS NSE (P10).
4. Rate-limit + size-cap on registration; the seal already caps plaintext (4 KB).
5. Re-run `notif-crypto.spec` + `encrypted-envelope.spec` on target hardware.

Until all five hold, leave the sub-flag OFF. The content-less floor is
never worse than today's shipped behaviour.
