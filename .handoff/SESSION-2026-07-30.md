## The theme of the day: two builds that lied

Two separate deployments had been broken for **days**, both reporting success
while serving stale code. Both had the same root cause in different clothes:

> **A build can only use what actually gets uploaded.**

1. **Railway** — `.deploy/` was in `spotme/backend/.gitignore`. `railway up`
   skips gitignored paths, so `npm run predeploy` staged `web/api` correctly on
   disk and the uploader silently dropped it. The Dockerfile's own assert then
   failed the build, and Railway kept serving the PREVIOUS container. This is
   why the previous session's Sarvam/cross-confirmation work "wouldn't land".
   A `.railwayignore` does **not** fix it — that file only ADDS exclusions and
   cannot override `.gitignore`. Staging moved to `deploy-api/`: untracked, but
   not ignored.

2. **Vercel** — `"spotme-core": "file:.."` resolved to `spotme/`, outside the
   only directory Vercel uploads. Every production build died on
   `Rolldown failed to resolve import "spotme-core/core/translit.js"`, and the
   site served **404 for days** while local builds passed (locally the parent
   directory is right there). Now a real local package at
   `web/vendor/spotme-core`, which must **never** be gitignored.

If a deploy ever looks like it "didn't take effect", check whether the build
actually succeeded before assuming it was a propagation delay. `railway logs`
defaults to the most recent **successful** deployment — pass the deployment id
explicitly or you will read the old one and see nothing wrong.

combination tried. The user supplied two new keys; both belong to the SAME
resource (identical `…ACHYHv6XJ3w3AAAbACOG` fingerprint), so what happened was

resource endpoint `ytranslator-yuvraj-2026.cognitiveservices.azure.com`. The

region variant. `azureBase()` already uses the resource endpoint — do not
"simplify" it to the global host.

speech-to-text. So while Azure was down, voice notes still transcribed and only

## Groups v2 (backend complete, no UI)

Decisions taken by the user:
- **Public groups use a server-held room key** → instant join by @username.
  The server CAN decrypt public-group traffic. Deliberate. Private groups keep
  strict E2E (key travels in the URL fragment, never sent to the server).
- **Unify onto one model** — room-based groups are the single source of truth.

Built: roles (OWNER/ADMIN/MODERATOR/MEMBER with strict rank ordering), granular
owner-set grants, ban/mute, ownership transfer, public groups with a globally
unique @username sharing ONE namespace with users, 30-day soft delete with a
purge sweep. 17 new tests, 26 across the suite.

**The most important part was not the roles.** The rooms gateway authorised
NOTHING — knowing a `roomId` was the entire access model, so a ban would have
been decorative and a removed member could rejoin and replay all history.
`join` and `action` are now checked against group policy.

**Known limit, documented in code:** the id of a message being deleted lives
inside the ciphertext, so the server cannot tell whose message it is. Clients
must send the original sender as cleartext `meta.owner`; absent that the delete
is allowed so older clients keep working.

**A test caught a real bug:** `setBan` stamps `leftAt` as well as `bannedAt`,
and `requireMember` tested `leftAt` first — so a banned user was told "not a
member". Ban now takes precedence.

The migration is hand-written because the required `roomId` needed a backfill;
it also ports legacy `ConversationParticipant` rows into `GroupMember` and
seeds `RoomMember`, without which migrated groups would have had zero members.

## Push notifications — the long one

**Starting state:** production held **ZERO** push subscriptions. For every
user. Ever. Not a delivery bug — nothing had ever registered.

**Why, definitively.** Ran the Chrome DevTools protocol against the app's
WebView on the emulator:

```
serviceWorker: true    PushManager: undefined    Notification: undefined
```

Capacitor's Android WebView has service workers but **no Push API and no
Notification API**. The packaged app can never receive Web Push under any
configuration. That is why "real-device delivery unverified" was never
resolved. A browser PWA can receive only Web Push; the packaged app only FCM.

**Built:** Firebase project `spot-messenger-48a74` + Android app for
`io.ysnapai.spotme` (created via CLI), `google-services.json` committed,
service-account key minted via gcloud into `.keys/` (gitignored) and set on
Railway as base64. New `DeviceToken` table. `notify()` now fans out to BOTH
transports so a phone and a desktop browser both light up.

**Two bugs found by running it, not reading it:**

1. The startup call gated on `Notification.permission === 'granted'`. That
   object does not exist in the WebView, so native registration was silently
   skipped and the phone would never have registered at all.
2. **Data-only messages were the wrong choice.** Chosen first to avoid handing
   content to Google. On-device they reached a backgrounded app and displayed
   NOTHING — Android never auto-renders data-only, and drops it once the
   process dies. The privacy argument was hollow: the payload carries no
   message text, only "New message". Now sends a notification block plus data.

**Verified end to end on the emulator** — a real chat message through the
server (`ack seq:1203`) triggered FCM and posted to the tray on an idle,
screen-off device. Test artifacts were cleaned up afterwards (1 RoomEvent row,
1 stray RoomMember).

**Android rule, not a bug:** FCM is never delivered to a **force-stopped** app
until the user launches it again. Normal backgrounding and swiping away work.

**Then a third bug, on the web side:** nothing ever ASKED for permission.
Startup only re-subscribed when already granted, and the only
`requestPermission()` call sat behind a toggle in profile settings. So a person
installed the app, never found that switch, and was never reachable — which is
exactly why production had zero subscriptions. A one-time sheet now appears
after onboarding. It must be a sheet with a button, because browsers only
honour `requestPermission()` from a user gesture.

**I broke the dev server and caught it.** Vendoring `spotme-core` as plain
aliased source dropped `optimizeDeps.include`, which is what applies Vite's CJS
interop — dev died on `does not provide an export named 'supportedScripts'`
while the production build survived, because Rollup handles CJS itself. Found
only because I checked the deployed site actually RENDERED rather than trusting
its HTTP 200.

## Late evening — the 404's actual cause, and Groups v2 shipped

**The Vercel 404 was never a code bug.** The project is git-linked to the repo
with `rootDirectory: null`, so every push built the REPO ROOT, produced an
empty `/vercel/output`, reported "Ready" in one second, and took the production
alias from the good CLI deploy. Both earlier "fixes" (vendoring `spotme-core`,
`c76f097`) were treating symptoms — the site died again minutes after each
push. `vercel inspect` showed it plainly: `Builds: . [0ms]`, no lambdas, versus
the known-good deployment's five `api/*` functions. Fixed by PATCHing
`rootDirectory: "spotme/web"` through the Vercel API (no CLI command exists).
The very push that shipped Groups v2 then deployed correctly and automatically.

**Groups v2 P3 (web UI) built and shipped** — `lib/groups-api.js`,
`lib/group-perms.js`, `views/group-new.js` (3-step wizard),
`views/group-manage.js`, rewritten `views/groups.js`, route `#/group/<id>`.
Driven in a real browser against the local backend, not mocks.

**Three bugs the build exposed**, none of which the 26 backend tests caught:
1. `ui.js el()` wrote `disabled="false"`; HTML treats a present `disabled` as
   disabled, so the wizard's Create button was inert from first paint. Two
   older call sites had worked around it (`disabled: fn ? undefined : ''`)
   instead of fixing the helper. Fixed in `el()`.
2. **Un-banning was impossible.** `setBan` stamps `leftAt` as well as
   `bannedAt`; `memberInclude` filtered on `leftAt` and `requireTarget`
   rejected it, so banned members vanished from every payload and the unban
   route answered 404 "that person is not in this group".
3. Lifting a ban cleared only `bannedAt`, leaving `leftAt` set and the
   `RoomMember` row deleted — back on the roster, still receiving nothing.

**Two silent-build traps recorded.** `nest build` exits 0 and emits NOTHING
when a stale `tsconfig.build.tsbuildinfo` meets `deleteOutDir: true` — and a
previous backend process kept holding :4000, so "the new route 404s" looked
like a code error when it was hours-old code. And Railway again served the
previous container for ~4 minutes after `npm run deploy` returned; a health
check could not tell the difference. Both were settled by exercising the
changed behaviour (ban → unban round trip), not by reading a status.

Caveat worth knowing: that production probe ran repeatedly while polling, so
roughly two dozen `qa_probe*` guest users now exist in the production database.
Each probe group was soft-deleted; the users were not.
